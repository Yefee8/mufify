# Internationalisation

English and Turkish, both first-class. Turkish is not a translation layer over
English — it is written as Turkish, and where the two languages want different
phrasing, they get different phrasing.

---

## Where things live

```
src/i18n/
  index.ts              # init, language resolution, changeLanguage
  locales/en.json       # the shape of the translation tree
  locales/tr.json       # must match en.json exactly
src/services/settings/
  language.ts           # LANGUAGES, resolveLanguage — pure, unit tested
  preferences.ts        # the stored preference
```

`i18next` + `react-i18next` + `expo-localization`. The stored preference lives
in MMKV, so it is read synchronously at boot and the app never renders a frame
in the wrong language.

---

## Adding a string

1. Add the key to `en.json`.
2. Add the same key to `tr.json`.
3. Use it: `const { t } = useTranslation(); t('settings.language.label')`.

Step 2 is not on the honour system. `en.json` is the source of the
`TranslationKeys` type and `tr.json` is checked against it, so a key added to
one and not the other fails `npm run typecheck` with the exact path:

```
Property '"label"' is missing in type ... but required in type ...
```

That is what enforces the `AGENTS.md` rule about both files changing in the
same commit.

### Key naming

Namespaced by feature, never the English sentence:

```
tabs.library          settings.appearance.theme
library.empty         settings.language.label
```

A key is a stable identifier. Rewording the English copy must not rename it.

## Language resolution

`resolveLanguage(preference, deviceLanguageTags)` is pure and unit tested in
`src/services/settings/language.test.ts`. The rules:

- An explicit preference (`en` / `tr`) always wins.
- On `system`, walk the device's preferred locales in order and take the first
  language we ship. Region is ignored: `tr-CY` is Turkish.
- Fall back to English when nothing matches.

The preference is a tri-state — `system`, `en`, `tr` — not a boolean. A user
who has never opened Settings gets their device language; a user who chose
Turkish on an English phone keeps Turkish.

## Turkish specifics

**Never uppercase user content.** Turkish has a dotted/dotless `i` pair, so a
JavaScript `toUpperCase()` turns `iyi` into `IYI` instead of `İYİ`, and `ı`
into `I`. If something genuinely must be uppercased, use
`toLocaleUpperCase('tr')`. In practice the design avoids this: copy is sentence
case everywhere, and there is no `text-transform` in the token system.

**Turkish runs 10–20% longer than English.** Layouts must survive it. The tab
bar is the tightest spot, which is why the Playlists tab reads `Listeler` while
the screen title is the fuller `Çalma listeleri` — the same idea at two lengths,
which is what a Turkish speaker would actually write.

**Register.** The app addresses the user informally (`seç`, not `seçiniz`),
which is normal for consumer apps and matches the plain-verb, no-marketing-voice
rule in the brief.

---

## Dates, numbers, durations

Format through `Intl` with the active locale. Never hand-roll, never
concatenate. Turkish uses `.` as the thousands separator and `,` as the decimal
separator — `2.304 kbps`, not `2,304 kbps` — and getting that wrong in the spec
strip would undercut the one screen element the app is built around.

The spec strip is the exception to nothing here: its numbers are localised, its
units are not (`kHz`, `kbps`, `MB` are the same in both languages).

## Adding a language

1. Add the code to `LANGUAGES` in `src/services/settings/language.ts`.
2. Add `src/i18n/locales/<code>.json`, complete — typecheck will list what is
   missing.
3. Register it in `resources` in `src/i18n/index.ts`.
4. Add its name to `settings.language.<code>` in **every** locale file, written
   in that language (`Türkçe`, not `Turkish`).
5. Check the longest strings against the tab bar and the settings segmented
   control.

Nothing else should need to change — no component holds a language list.
