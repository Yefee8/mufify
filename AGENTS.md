Instructions for AI coding agents working in this repository.

## Project

An offline-only local music player for Android, built with React Native and Expo.
Plays FLAC and other lossless formats from the device. Local playlists, multiple shuffle
algorithms, on-device listening statistics, dark/light themes, Turkish and English.

**No network. No accounts. No telemetry. No analytics SDK.** If a change introduces a network
call, it is wrong. This is the app's core promise and the reason it exists.

## Setup

Requirements: Node 22+, JDK 17 or 21, Android Studio with SDK Platform 35+, macOS or Linux.

### Environment (macOS)

None of this is set by default. Put it in `~/.zshrc` — every "it works on my machine" failure in
this project so far has been one of these three lines missing.

```bash
# Android Studio's bundled JBR is a perfectly good JDK. No separate install needed.
export JAVA_HOME="/Applications/Android Studio.app/Contents/jbr/Contents/Home"
export ANDROID_HOME="$HOME/Library/Android/sdk"
export PATH="$JAVA_HOME/bin:$ANDROID_HOME/platform-tools:$ANDROID_HOME/emulator:$PATH"
```

Verify before blaming the code:

```bash
java -version        # 17 or 21
adb devices          # your device, "device" not "unauthorized" or "offline"
npx expo-doctor
```

### Daily loop

```bash
npm install
npx expo start --dev-client   # this is the normal one — JS/TS changes hot reload
npm run lint
npm run typecheck
npm test
npm run db:generate           # drizzle-kit: generate migration after schema change
```

`npx expo run:android` is **only** for native changes: adding or removing a native dependency,
editing `app.json`, or changing a config plugin. It is a ten-minute build. Reaching for it after a
TypeScript edit is the most common way to waste an afternoon here.

### Installing on a device

`adb install` is enough on most phones and on the emulator. On **MIUI / HyperOS (Xiaomi, Redmi,
POCO)** it fails with `INSTALL_FAILED_USER_RESTRICTED` — MIUI blocks installs over USB regardless
of what the developer options say. Push the APK and install it from the device instead:

```bash
adb push android/app/build/outputs/apk/debug/app-debug.apk /sdcard/Download/
# then open Files → Download → app-debug.apk on the phone and confirm
```

Turning on "Install via USB" in MIUI developer options needs a signed-in Xiaomi account and often
still fails; the push route is faster and always works.

### Emulator

The Pixel AVD wants ~5 GB of RAM. If the host is short, it dies with SIGABRT mid-session, usually
in the graphics stack. Headless survives that and screenshots still work:

```bash
emulator -avd Pixel_7 -no-snapshot -no-boot-anim -no-window -gpu swiftshader_indirect -memory 2048
adb exec-out screencap -p > shot.png
```

**Anything about audio must be verified on a physical device.** Emulator audio output tells you
nothing true about 24/96 playback, gapless, or the foreground service surviving a screen-off.

`minSdkVersion` is **26**, set through `expo-build-properties` in `app.json`. Raising it to 31
was considered and rejected: it costs roughly a fifth of Android devices while deleting almost no
code, because `READ_MEDIA_AUDIO` is API 33 and the `MediaMetadataRetriever` fields need null
handling at every API level anyway. See `docs/adr/002-min-sdk-26.md`.

`android/` and `ios/` are generated by Continuous Native Generation and are **git-ignored**.
Never hand-edit them. Native configuration goes in `app.json` / config plugins.

## Architecture rules

These are not preferences. Violating them is a bug.

1. **`app/` contains routes only.** Route files are thin: they read params, render a screen
   component, and nothing else. No queries, no logic.
2. **Only `src/services/audio/*` may import the audio playback library.** Everything else talks
   to `AudioEngine`. This keeps the engine swappable — see the licensing situation documented in
   `docs/player.md`.
3. **Only `src/db/queries/*` may import Drizzle or `expo-sqlite`.** Components and hooks call
   typed query functions.
4. **No business logic in component bodies.** Logic goes in `src/services/` (pure, testable) or
   `src/features/*/hooks/` (stateful orchestration).
5. **Settings live in MMKV. Data lives in SQLite.** Don't mix them. Zustand holds transient
   player/UI state only, never anything that must survive a restart.
6. **Layers point downward.** `components → hooks → services → db`. Never the reverse. A service
   must not import a component.

## Code style

- TypeScript `strict`. No `any`. No `@ts-ignore` without a comment saying why and what would
  remove it.
- **Components under 300 lines.** Over 300 means it should be two components. This is checked in
  review and is a hard limit, not a guideline.
- One component per file. File name matches the component name: `TrackRow.tsx` exports `TrackRow`.
- Named exports everywhere except route files, which need a default export for expo-router.
- Function components with hooks. No class components.
- Props interfaces named `<Component>Props`, defined in the same file, exported.
- Imports ordered: react → react-native → third-party → `@/…` internal → relative. Use the `@/`
  alias for `src/`; no `../../..` chains.
- Naming: `PascalCase` components, `camelCase` functions and variables, `SCREAMING_SNAKE` module
  constants, `use*` hooks, `*.types.ts` for shared type modules.
- Async functions that can fail return a result or throw a typed error — never swallow an error
  into a silent `null`.

## Styling

- **NativeWind only.** No `StyleSheet.create`, no inline `style` objects, except where NativeWind
  genuinely cannot express it (animated styles from Reanimated worklets are the main exception).
- Use **semantic** class names from the theme, never raw palette values:
  `bg-surface`, `bg-surface-elevated`, `text-primary`, `text-muted`, `border-subtle`,
  `bg-accent`. Never `bg-indigo-600` or `bg-[#4f46e5]` in a component.
- **Colours do not take a `dark:` variant.** Both themes are defined once, as CSS variables in
  `src/theme/global.css`, and the variable flips with the theme. A component writes `bg-surface`
  exactly once. This is deliberate: it makes a single-theme colour impossible to define, which is
  what the old "every colour needs both" rule was trying to achieve by hand. The `dark:` variant
  is still correct for non-colour differences (a border that only exists in light mode).
- Design dark first. Light is derived from it.
- Design tokens are defined in one place (`src/theme/global.css` and `src/theme/tokens.ts`).
  Adding a colour means adding a token, not a hex value in a component. The two files are kept in
  sync by hand and `src/theme/tokens.test.ts` fails on drift — do not replace it with a generator.
- The Tailwind config **overrides** rather than extends the colour, spacing and radius scales, so
  `bg-indigo-600` and `rounded-2xl` produce no output at all. If a class silently does nothing,
  that is why: it is not in the design system.
- **`className` only works on components NativeWind knows.** A third-party component receives it
  as an unrecognised prop and renders unstyled — no warning, no error, just a view with no size.
  Register it once in `src/theme/interop.ts` with `cssInterop`. This cost an afternoon: artwork on
  `expo-image` was `h-10 w-10`, drew at zero by zero, and collapsed the row — but only for tracks
  that *had* a cover, because the placeholder was a plain `View` and looked fine.
- Spacing from the scale only. No arbitrary values like `p-[13px]`.
- Contrast is a hard constraint, not a preference: ≥ 4.5:1 for body text in both themes, asserted
  in `tokens.test.ts`. On a filled indigo surface use `text-on-accent` and never white — white on
  the dark-theme indigo is 2.98:1 and fails.

## States

**Every screen and every component is designed with its empty, loading and error states from the
start.** Not in a polish phase, not "when we have real data" — in the same commit as the happy
path. A screen submitted with only its populated state is incomplete, the same way a component
without a type is incomplete.

Concretely, before a screen is done, answer all three:

- **Empty** — there is no data yet. Use `<EmptyState />`. An empty screen is an invitation, not a
  failure: say what is missing and put the action right there.
- **Loading** — data is coming. Skeletons that match the shape of the real content, never a
  centred spinner on a blank screen, never a layout that jumps when data lands.
- **Error** — something failed. Say what failed in one plain sentence and offer the retry. Never
  a raw error string, never a dead end.

Tone across all three: sentence case, no apologies, no mascots, no emoji. Light wit is allowed if
it sounds like the rest of the app; nothing that sounds like a different product wrote it.

This applies to the phases ahead. UI and UX are part of the first pass, not a later cleanup.

## Internationalisation

- **Every user-facing string goes through `t()`.** No exceptions, including error messages,
  accessibility labels, and empty states.
- `en.json` and `tr.json` are updated in the **same commit**. A PR that adds a key to one and not
  the other does not merge.
- Keys are namespaced by feature: `player.nowPlaying`, `stats.topArtists`, `settings.shuffle.title`.
  Never use the English sentence as the key.
- Dates, numbers and durations format through `Intl`, with the active locale. Never hand-roll.
- Turkish specifics: don't uppercase user content (the İ/ı problem); if you must, use
  `toLocaleUpperCase('tr')`. Turkish strings run roughly 10–20% longer than English — layouts
  must not break.

## Performance rules

The app must stay fluid with a 10,000-track library. Concretely:

- **All long lists use FlashList.** `FlatList` is not acceptable for track lists.
- `renderItem` renders a memoized component and receives **no inline arrow functions**. Pass the
  id and a stable callback from `useCallback`.
- **Never decode embedded artwork at render time.** Artwork is extracted once during scanning,
  resized, written to the cache directory, and referenced by path.
- Images go through `expo-image` with an explicit `recyclingKey` and `cachePolicy`.
- **Statistics screens read `stats_rollups` only.** Never aggregate `play_events` in a screen
  query. Rollups are updated incrementally when a play event is recorded.
- **A count and the list it describes come from one query.** Two live queries over the same table
  drift, and the screen then reports a number it cannot show — the library header once read
  "14 tracks" above nothing. If a screen shows both, the count is `list.length`.
- Scanning work is chunked and yields to the UI thread. The user can always scroll during a scan.
- DB writes during scan are batched in transactions of ~500 rows.
- Playback progress animates in a Reanimated worklet — it does not set React state 60 times a
  second.

Before claiming a performance fix, measure it and report the numbers.

## Testing

- Unit tests are required for anything pure: shuffle algorithms, period-key computation, the
  play/skip counting rule, formatters, the incremental rollup logic.
- Shuffle algorithms take an injected RNG so tests are deterministic. Test the *property*
  (e.g. "balanced never places two tracks by the same artist within N positions"), not one
  hardcoded output.
- Rollup correctness is tested by comparing incremental rollups against a brute-force recount
  over `play_events`.
- Component tests only where behaviour is non-obvious. Don't test that a `<Text>` renders text.
- `npm test`, `npm run lint` and `npm run typecheck` must all pass before a commit is considered
  done.

## Documentation

Docs are part of the work, not cleanup afterwards.

- `docs/architecture.md` — the layer diagram and why the boundaries exist
- `docs/database.md` — schema, indexes, the play-counting rule, migration process
- `docs/player.md` — AudioEngine interface, background playback, the Android foreground-service
  gotchas, why this engine was chosen
- `docs/scanner.md` — the two-stage scan, incremental rescan, artwork cache
- `docs/shuffle.md` — each algorithm explained in plain language, with its trade-offs
- `docs/stats.md` — event recording, rollups, period keys and timezone handling
- `docs/components.md` — the component tree and what each shared component is for
- `docs/theming.md` — the token system and how to add a colour
- `docs/i18n.md` — how to add a string and a language

Any non-obvious decision gets a short ADR in `docs/adr/NNN-title.md`: context, decision,
consequences. Three paragraphs is plenty.

Every exported component and service function has a one-line JSDoc saying what it does. Skip the
comments that restate the code.

## Commits and PRs

- Conventional commits: `feat:`, `fix:`, `refactor:`, `perf:`, `docs:`, `test:`, `chore:`.
  Scope where useful: `feat(shuffle): add discovery algorithm`.
- One logical change per commit. Never one commit per phase of work.
- PR description says what changed, why, and how it was verified on a device.
- Don't commit generated native directories, `.env`, or anything with a key in it.

---

## Do not

- Add a network request, analytics, crash reporting, or any third-party SDK that phones home.
- Add a dependency without justifying it — bundle size and native build time are real costs.
  Check the license; this project ships under an OSI-approved license and cannot take
  source-available or commercially-licensed dependencies.
- Hand-edit `android/` or `ios/`.
- Store artwork bytes, base64 blobs, or file contents in SQLite.
- Hardcode a colour, a spacing value, or a user-facing string.
- Write a component over 300 lines and promise to split it later.
- Delete a track row during rescan because the file is temporarily missing — mark
  `is_missing = 1` instead, so playlists and history survive an unmounted SD card.
- Claim something works without running it on a device or emulator.

## When you're unsure

State the uncertainty, propose the two options with trade-offs, and ask. A five-line question is
cheaper than a day of work in the wrong direction.

If a requirement in the brief conflicts with something you've learned in the code, say so
explicitly rather than quietly building around it.

This stack changed significantly in 2025–2026 (New Architecture became mandatory, the default
audio library changed license, NativeWind changed major version). **Check current documentation
instead of relying on memory** — half-remembered APIs from an older version are the most likely
source of wasted time in this project.
